# 02 — Функциональный аудит

Версия: 0.75.1. Статусы по методологии ТЗ: **Работает** / **Частично работает** / **Не работает** / **Не реализовано** / **Требует проверки**. «Работает» здесь означает «подтверждено по коду и/или зафиксировано в предыдущем UI-тесте (`AUDIT-2026-10-29.md`, 469/469 unit + browser smoke)», а не «проверено заново вживую в рамках этого этапа» — живых прогонов в этом этапе не было (раздел 19, см. также 09-TEST_RESULTS.md).

## Главная страница (раздел 4 ТЗ)

| Критерий | Оценка |
|---|---|
| Понятность текущего состояния игрока | Частично — `HomeBanner`/`PlayerCard` показывают уровень, XP, сферы; на 23.10 пользователь сам отмечал перегруженность (TODO.md: «убрать верхнюю панель аккаунта», «убрать трекер привычек и полосу игрока с главной карточки сфер») |
| Количество задач видно | Работает — «Мои задачи на сегодня» на главной (сохранено по TODO.md) |
| Прогресс дня | Работает | 
| Активные цели (проекты) видны | Частично — TODO.md фиксирует намерение заменить «Главную цель»/«Ближайшую награду» на 3 выбираемых главных проекта месяца; требует проверки текущего состояния в живом UI |
| Ближайшие дедлайны | Требует проверки |
| Быстрое создание задачи | Работает — быстрые действия «+ Новое задание» (0.14.3) |
| Переход к планированию | Работает — прямая ссылка на «Мои задачи»/«Мой план» |
| Игровые показатели | Работает — XP, уровень, монеты, серия |
| Лишние/дублирующие блоки | **Да, зафиксировано самим пользователем** в TODO.md от 23.10: дублирование «Сегодня» на карточках сфер и в отдельном блоке, статичная «Ближайшая награда» |
| Перегрузка интерфейса | Частично — TODO.md прямо описывает план разгрузки главной (верхняя панель аккаунта → в профиль) |

**Статус бэклога TODO.md:** документ датирован 23 октября (версия тогда ~0.52), содержит невыполненные чек-боксы `[ ]`. Текущая версия 0.75.1 добавила «Главная: XP годовая сводка» (`HomeYearSummary.tsx`) — что совпадает по смыслу с одним из пунктов TODO.md, но сам файл TODO.md не обновлён и не помечен выполненным. **Расхождение документации с кодом**: нельзя полагаться на TODO.md как на актуальный бэклог без сверки созданных компонентов.

## Управление задачами (раздел 5 ТЗ)

| Возможность | Статус | Подтверждение |
|---|---|---|
| Создание | Работает | `TaskCreationForm.tsx`, `QuestWizard.tsx` |
| Изменение | Работает | `TaskWindow.tsx`, `taskSettings.ts` |
| Удаление | Работает | меню «⋯» (0.73.0) |
| Восстановление | Частично | есть `wontDo` (обратимая отметка «не буду делать»), прямого «восстановить удалённую задачу» (корзина) не найдено — удаление похоже на необратимое. **Требует проверки** |
| Выполнение / отмена выполнения | Работает | `completeQuest`, `reopenQuest` (`planning-system-2.0/AUDIT.md`, раздел 25) |
| Дублирование | Работает | пункт меню «⋯» (0.73.0, CHANGELOG) |
| Подзадачи | Работает | `Quest.subtasks` (`game.ts:152`); сбрасываются при повторении серии |
| Приоритеты | Частично | только `low/normal/high` (`game.ts:147`), не P1–P4 TickTick-style; плюс отдельные булевы `important`/`urgent` в `planningData.ts` для матрицы Эйзенхауэра — **два параллельных механизма приоритизации**, потенциальная путаница |
| Дедлайны | Работает | `Quest.deadlineAt` — отдельное поле от плановой даты (0.19, намеренное разделение) |
| Плановые даты | Работает | `startsAt`/`dueAt`, зеркалятся из TickTick, read-only если задача связана |
| Плановая продолжительность | Работает | `estimateMinutes` |
| Фактическое время | **Не реализовано** | `planning-system-2.0/AUDIT.md` п.9 прямо фиксирует отсутствие факта/таймера |
| Повторения | Работает | daily/weekdays/weekly/monthly; нет «каждые N дней», «ежегодно», «конец серии» — см. 04-PLANNING_GAP_ANALYSIS.md |
| Напоминания | Не реализовано (в игре) | нет поля reminder в `Quest`; push/локальные уведомления не найдены в коде |
| Категории / сферы жизни | Работает | `Quest.sphere`, 10 сфер |
| Привязка к целям/проектам/этапам | Работает | `goalId`, `stageId` |
| Фильтры | Частично | `PlanningWorkspace.tsx` фильтрует по виду/владельцу; сохранённых пользовательских фильтров не найдено |
| Сортировка | Требует проверки | не выявлена явная настройка сортировки в просмотренных файлах |
| Поиск | Работает | `globalSearch.ts` |
| Массовые операции | Не реализовано | не найдено массовое выполнение/удаление/перенос нескольких задач разом |
| Архивация | Работает | `planning.archivedAt` поле (`planningData.ts:8`) |
| История изменений | Частично | `Event`-журнал (`game.ts:261`) фиксирует события, но это общий игровой журнал наград/счёта, не полная история правок полей задачи |
| История переносов | **Не реализовано как отдельный журнал** | Подтверждено дважды (`planning-system-2.0/AUDIT.md` п.8, этот аудит): есть «Активность» в `TaskWindow` по `state.events`, но нет структурированной истории «дата N → дата N+1, причина» с подсчётом числа переносов |
| Синхронизация | Работает | Firebase + TickTick, см. раздел 15 |

**Скорость создания задачи:** быстрая кнопка «+ Новое задание» с главной + форма в разделе «Мои задачи» — минимум действий (1 клик до формы). Оценка: соответствует современным планировщикам, отдельного упрощения не требуется.

**Различие задача/мини-квест/бизнес-задание:** в текущей модели **единая сущность `Quest`** с полями `sourceType: 'SYSTEM' | 'USER_CREATED'` и `difficulty`. Отдельных типов «мини-квест»/«бизнес-задание» как разных сущностей в коде не найдено — похоже, это либо устаревшая терминология из старых версий, либо различие только по `sphere`/`difficulty`. Общая модель данных уже объединяет типы — архитектурно это сделано правильно.

## Планирование времени (раздел 6 ТЗ)

| Уровень | Реализовано | Отсутствует |
|---|---|---|
| День | Список на сегодня (`TodayTasks.tsx`), дневной фокус через `mainLimit`, завершение дня — нет явного ритуала «закрыть день» | Расписание по часам внутри дневного вида, явная обработка непройденных задач при завершении дня |
| Неделя | Недельный вид календаря, drag-and-drop, `weekLoad` расчёт нагрузки | Мастер подтверждения недели (зафиксирован как отсутствующий в `planning-system-2.0/AUDIT.md`, п.5), недельный шаблон/копирование |
| Месяц | Месячный календарь, `monthlyFocus` (до 3 проектов) | Создание задачи прямо из ячейки месяца, единые кросс-видовые фильтры |
| Квартал/год | **Не реализовано** | Нет отдельного квартального/годового планировщика; есть только годовой *отчёт* (`YearReport`), это аналитика, не планирование вперёд |

## Календарь (раздел 7 ТЗ)

Режимы: день / неделя / 2 недели / месяц (`TasksCalendar.tsx`) — подтверждено. Перенос задач drag-and-drop — подтверждено. Изменение длительности через `onResize` — подтверждено. Готовность к Time Blocking: **частичная** — `startsAt`/`dueAt` хранят интервал, но нет отдельной сущности «временной блок» (можно создать несколько блоков под одну задачу, показать конфликт пересечения по времени) — специальной проверки пересечений интервалов в просмотренном коде не найдено, требуется точечная проверка `tasksCalendar.ts`.

## Цели и карты пути (раздел 8 ТЗ)

«Карта личного/профессионального/семейного пути» как отдельных сущностей не найдено — есть единая `LifePlanMap.tsx` + `lifePlanMap.ts` с `KeySpheres`, что мэппится на 10 сфер жизни, а не на 3 отдельные карты (личная/профессиональная/семейная) из формулировки ТЗ. **Расхождение формулировки ТЗ с архитектурой приложения**: в PLAY YOUR LIFE карта пути одна, по сферам, а не по 3 измерениям жизни.

Прогресс цели: два режима — `progressMode: 'manual' | 'tasks'` (`game.ts:233`). При `tasks` прогресс считается от выполненных связанных задач — то есть **автообновление прогресса по задачам уже реализовано**, не требует новой архитектуры. Дублирования расчётов не найдено — обе ветки используют общий `Goal.current/target`.

## Проекты (раздел 9 ТЗ)

Подтверждено (раздел 01): Goal = проект, с этапами (`GoalStage`), паузой, темпом, недельным фокусом, WOOP, «если-то», контрольными точками, заметками, финальным результатом, обзором (`ProjectReview`) при завершении. Канбан/Гант на уровне самого проекта **не реализованы** (только декоративный канбан в 3D-комнате — не функция). Зависимости задач реализованы на уровне задач (0.75.0), не на уровне этапов/проектов.

Проект представлен только как цель с этапами — отдельной сущности «Проект» нет и по решению пользователя (зафиксировано в `planning-system-2.0/AUDIT.md`, п.14) вводиться не будет — осознанный архитектурный выбор, не упущение.

## Привычки (раздел 10 ТЗ)

Отдельная модель `Habit`/`HabitCompletion` (`personalQuests.ts`), не путается с `Quest.repeat` на уровне данных — это два разных механизма. Серии (`currentStreak`/`bestStreak`), статистика, награды — есть. Привязки к сфере — есть (`Habit.sphere`). **Привязки к цели/проекту — нет** (поля `goalId` в типе `Habit` не найдено). Напоминаний — нет. Описание/своя картинка — не найдены в типе `Habit` (CHANGELOG 0.21.0 ранее фиксировал это как известный пробел; на 0.75.1 подтверждено повторно — поля действительно отсутствуют).

## Контроль переносов (раздел 11 ТЗ)

| Вопрос | Ответ |
|---|---|
| Сохраняется исходная дата | Частично — `mainDay` (`planningData.ts`) существует, но прямого поля «originalDueDate» не найдено |
| История переносов | Не реализована как структурированный журнал (см. раздел 5 выше) |
| Количество переносов определимо | Нет — без журнала переносов посчитать нельзя |
| Просроченные задачи отображаются | Работает — группа «Просрочено» в `TodayTasks`/календаре |
| Автоперенос | Не реализован |
| Анализ причин переносов | Не реализован (хотя `PlanningChange` в `planningData.ts:21-23` уже содержит необязательное поле `reason` — заготовка под это есть, но не используется для аналитики) |
| Контроль перегрузки | Частично — `moveWarning` в `PlanningSettings` (порог предупреждения о переносах) и `wipLimit`/`dailyMinutes`/`reservePercent` — заготовка для контроля нагрузки существует в данных, но её фактическое применение в UI (показывается ли предупреждение) не проверено построчно — **требует проверки** |

## Аналитика (раздел 12 ТЗ)

Подтверждённые разделы: `KeyResults.tsx`, `MonthReport.tsx`, `MyResults.tsx`, `Statistics.tsx`, `yearReport.ts`, `sphereAnalytics.ts`, `goalStatistics.ts`. Это значительный, работающий аналитический слой (902 строки документации `docs/KEY-RESULTS.md` + план редизайна существуют). Completion Rate / Plan Accuracy / Task Postponement Rate / Project Momentum как отдельных именованных метрик по этим точным названиям **в просмотренных файлах не найдены** — вероятно считаются другими именами или не выделены как отдельные карточки. Требует точечной сверки с `keyResults.ts`/`sphereAnalytics.ts` построчно (не выполнено в рамках бюджета этого прохода — отмечено как «Требует проверки», не «отсутствует», чтобы не придумывать пробел).

Фиктивные/статические данные в графиках: не обнаружены явные моки в просмотренном коде (`sphereAnalytics.ts`, `goalStatistics.ts` оперируют реальными `events`/`quests`); специальной построчной проверки каждого графика не проводилось.

## Игровая механика (раздел 13 ТЗ)

Сильная сторона проекта. XP/уровни/HP(?)/монеты/квесты/достижения/награды/магазин/город/здания/комнаты — всё подтверждено по файлам раздела 01. **HP** как отдельный игровой параметр **не найден** в `GameState`/`PlayerProfile` — в ТЗ фигурирует «HP» (здоровье персонажа), но модель данных его не содержит; возможно, в ТЗ это ошибочное ожидание от игры другого типа, либо HP нигде не выведен на экран. Требует уточнения с пользователем (вопрос вынесен в 10-EXECUTIVE_SUMMARY.md).

Анти-дублирование наград: `firestore.rules` реализует серверную проверку через `questProof`/`habitProof`/`receipt` с привязкой к `transactionId`, что по конструкции исключает повторное начисление одной и той же награды на уровне правил безопасности — это весомое архитектурное подтверждение (не просто «в коде клиента проверяется»). Отмечено в `AUDIT-2026-10-29.md` как нерешённый риск только для XP (нет серверного **потолка роста** XP, в отличие от монет) — `AUD-007` остаётся открытым на 0.75.1 (не найдено подтверждений исправления в CHANGELOG).

## TickTick (раздел 14 ТЗ)

См. отдельно `04-PLANNING_GAP_ANALYSIS.md` и `docs/TICKTICK.md`/`docs/TICKTICK-SETUP.md` (уже подробно задокументировано самим проектом). Коротко: OAuth per-user, сопоставление списков со сферами, двусторонняя синхронизация задач (создание/обновление/выполнение/приоритет/даты/повторы), привычки через официальный TickTick MCP-сервер, защита от дублирования (`ticktickSafety` тесты). Известный исправленный баг — round-trip приоритета (0.62.5). Производственная (live, с реальным аккаунтом) проверка не выполнялась в этом аудите.

## Хранение и синхронизация (раздел 15 ТЗ)

Firebase/Firestore, с `accountPersistence.ts`, `firebaseSave.ts`, `stateValidation.ts`, `stateMerge.ts`, `backup.ts`, `revisionConflict.ts`, `cloudSplit.ts` — многослойная архитектура сохранения с ревизиями, конфликтами, бэкапом и разбиением больших документов на части (`cloudSplit.ts`, `historyIndex`/`imageRefs` в `GameState`). Подтверждено прошлым аудитом: 14/14 тестов правил безопасности на эмуляторе, два клиента на общем облаке корректно обмениваются изменениями. **Production Firebase не проверялся** ни в прошлом, ни в этом аудите — это явная и заявленная граница (см. `docs/FIREBASE.md`).

## Вывод

Функционально приложение покрывает подавляющее большинство требований ТЗ **на уровне архитектуры и кода**. Главные подтверждённые разрывы: фактическое время выполнения, структурированная история переносов, массовые операции над задачами, напоминания, квартальное/годовое планирование вперёд, Гант/зависимости на уровне проектов. Все перечислены как самостоятельные пункты в `04-PLANNING_GAP_ANALYSIS.md` и приоритизированы в `03-BUG_REPORT.md`/`08-DEVELOPMENT_ROADMAP.md`.
