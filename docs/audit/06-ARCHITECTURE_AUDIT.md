# 06 — Технический и архитектурный аудит

Версия: 0.75.1.

## Архитектура и зависимости

- Стек: React 19, TypeScript ~5.9 (`strict: true`, `noUnusedLocals`, `noUnusedParameters` — строгая конфигурация, не минимальная), Vite 7, Firebase 12 (Firestore), Three.js 0.180 + @react-three/fiber/drei для 3D.
- `tsconfig.json`: `strict: true` — хорошая база; `isolatedModules`, `allowImportingTsExtensions` — современная ESM-ориентированная сборка.
- `package.json → overrides`: закреплён `@grpc/grpc-js@1.14.5` — осознанная фиксация версии транзитивной зависимости (вероятно, из-за известной проблемы совместимости с Firebase SDK) — нормальная практика, не риск.
- Отдельный `tsconfig.json` для `integrations/ticktick/` — TickTick-бридж физически и типово изолирован от основного клиента, что снижает риск случайной связности между игровым клиентом и серверным прокси.
- Node `engines: ">=24 <25"` — жёстко зафиксированная мажорная версия Node, что снижает «works on my machine» риски в CI/Codespaces.

## Структура компонентов и разделение бизнес-логики

- `src/components/` (161 файл) — UI-слой. `src/*.ts` (верхний уровень, ~90 файлов) — бизнес-логика без JSX: экономика (`questEconomy.ts`), сохранения (`firebaseSave.ts`, `stateValidation.ts`, `stateMerge.ts`), планирование (`planning.ts`, `planningData.ts`, `taskDependencies.ts`), город (`city.ts`, `cityLive/`).
- Это **в целом здоровое разделение** UI/логики — бизнес-правила (например, проверка циклов зависимостей, валидация планирования) живут вне React-компонентов и поэтому тестируемы напрямую unit-тестами (`tests/*.test.ts` — 80+ файлов, именно по этим модулям, не по компонентам).
- `AGENTS.md` формализует «зоны файлов» между Claude Code и Codex (игровая логика/сохранения — Claude Code; компоненты/стили — Codex; тесты/CI — Codex) — это снижает риск конфликтов при параллельной работе нескольких ИИ-инструментов, но одновременно означает, что **архитектурные решения по данным принимаются отдельно от UI-решений** двумя разными исполнителями — есть риск рассинхронизации (пример — найденные два параллельных механизма приоритета, см. 03-BUG_REPORT.md), которая обычно и возникает на стыке таких зон.
- `game.ts` — 2036 строк, центральный файл типов и констант. Это самый крупный файл в проекте и потенциальная точка конфликтов при параллельном редактировании (упомянут в таблице зон `AGENTS.md` как зона Claude Code целиком).

## Типизация

- Модель данных (`Quest`, `Goal`, `GoalStage`, `Habit`, `GameState` и т.д.) — полностью типизирована, с явными union-типами для перечислений (`priority`, `repeat`, `rarity`, `workflow`) вместо «голых строк» — хорошая практика, снижает число runtime-ошибок от опечаток.
- Множество полей опциональны (`?:`) — ожидаемо для эволюционирующей модели данных с историей миграций без ломающих изменений (ни одна версия не требовала миграции схемы, судя по `CHANGELOG.md`/`AGENTS.md`), но увеличивает число мест, где нужна defensive-проверка `undefined`.
- Валидационные функции (`validTaskPlanning`, `validDependencyIds`, `validDependencyGraph`) написаны как чистые функции с runtime-проверкой типов — соответствуют данным, которые приходят из недоверенного источника (Firestore, TickTick), а не только компилятору TS — правильный подход для границы клиент/облако.

## Управление состоянием

- Нет Redux/Zustand/MobX — состояние хранится как единый `GameState`-объект и обновляется через чистые функции-трансформеры (`setTaskWorkflow(state, ...)`, `changeTaskPlanning(state, ...)`), которые затем сохраняются целиком в Firestore (`firebaseSave.ts`). Это простая и предсказуемая модель «один источник правды», которая хорошо сочетается с офлайн-черновиками и слиянием ревизий (`stateMerge.ts`, `revisionConflict.ts`).
- Риск такого подхода при росте — размер документа Firestore и частота полных перезаписей; это явно осознано командой: `cloudSplit.ts` уже выносит историю и обложки изображений в отдельные документы (`historyIndex`/`imageRefs` в `GameState`) — архитектурный ответ на этот риск уже есть, не требует нового проектирования, только расширения по мере роста новых журналов (например, будущей истории переносов).

## Обработка ошибок

- `ErrorBoundary.tsx` присутствует на уровне приложения — подтверждено как внедрённое в `AUDIT-2026-10-29.md` («error boundary вместо белого экрана», 0.40.0).
- `saveError.ts` — отдельный модуль для классификации ошибок сохранения.

## Производительность

- `LifeCity` (самый тяжёлый 3D-раздел) загружается через `React.lazy`/`Suspense` — не входит в стартовый бандл (`AUDIT-2026-10-29.md`: отдельный чанк 66.11 КБ / 24.42 КБ gzip на 0.64.6).
- Бюджеты размера контролируются скриптом `scripts/check-budgets.mjs` в CI — JS/CSS gzip-бюджеты явно заданы и проверяются автоматически (не вручную на глаз) — сильная инженерная практика. На 0.73.x CSS был на 99% лимита (`AUD-009`, см. 03-BUG_REPORT.md) — единственный найденный риск по этому пункту.
- Мобильная производительность 3D-города ранее измерялась отдельно (56 FPS на 1440px desktop, целевые 30 FPS на тестовых телефонах, по `AUDIT-2026-10-29.md`) — не переизмерялась на 0.75.1 в рамках этого аудита.

## Безопасность хранения данных и правила доступа

- `firestore.rules` (165 строк) — не формальность: содержит функциональную валидацию каждого начисления награды (`validRecord`, `questProof`, `habitProof`, `receipt`) с привязкой к `transactionId`, проверкой диапазонов XP/монет по таблице сложности, и изоляцию по `userId` (`match /players/{userId}`, функция `owner()`). Это заметно выше среднего уровня строгости для типового pet-проекта — видно целенаправленное проектирование против накрутки/дублирования наград на уровне инфраструктуры, а не только клиента.
- Единственный подтверждённый открытый пробел — отсутствие серверного потолка **суммарного** роста XP (`AUD-007`, см. 03-BUG_REPORT.md) — зафиксированный, осознанный, низкоприоритетный на сегодня риск.
- Production-правила и реальные данные не проверялись «вживую» ни разу за три подряд проведённых аудита (29 окт, 7 ноя, этот) — только через эмулятор. Это системное ограничение методологии (безопасно для данных пользователя), а не находка аудита.

## Тестовое покрытие

- **91 тестовый файл** (`find tests -type f`): TS unit-тесты (`.test.ts`, ~80 файлов) через встроенный `node --test`, плюс отдельные UI/браузерные скрипты (`.mjs`, ~11 файлов: smoke, goals-ui, planner-ui, tasks-calendar-ui, live-city-ui, theme-ui, spheres-ui, key-results-ui, month-report-ui, quests-ui, ticktick-flow-ui, spellcheck-ui, logo-ui, home-ui).
- Последний подтверждённый прогон (на момент сверки Planning System 2.0, 7 ноя, 0.73.2+): **502/502** unit-тестов, 14/14 правил Firestore на эмуляторе. На 0.75.1 число тестов не пересчитывалось в рамках этого аудита (не запускалось локально по стандартному правилу проекта — проверка только через CI, см. `09-TEST_RESULTS.md`).
- Firestore-правила покрыты отдельным набором тестов через `@firebase/rules-unit-testing` (`tests/firebase-rules.test.mjs`) — это значит, что сама логика защиты от повторных начислений (см. раздел выше) **протестирована**, не только написана.

## Сборка и развёртывание

- `npm run check` = lint + build, единая команда для CI-гейта (`Project checks`).
- `.github/workflows/ci.yml` (Project checks) и `.github/workflows/pages.yml` (деплой) разделены — деплой происходит только после прохождения проверок на `main` (подтверждено логами `gh run list`: `Deploy to GitHub Pages` запускается через `workflow_run` после успешного `Project checks`).
- Отдельный workflow «Verify coastal city and 3D rooms» — необязательный визуальный regression-тест 3D-комнат, **сейчас падает** на шаге скриншота (см. `03-BUG_REPORT.md`, P2) — не блокирует публикацию, но ослабляет визуальный контроль 3D-разделов.
- GitHub Pages деплой работает без ручного шага — соответствует заявленному в `README.md`.

## Итоговая оценка архитектурных рисков

| Область | Риск | Уровень |
|---|---|---|
| Серверный потолок XP | AUD-007 | Низкий сегодня, вырастет при мультиплеере/рейтингах |
| CSS-бюджет на пределе | AUD-009 | Средний — ближайший же UI-патч может его пробить |
| Падающий визуальный CI для 3D-комнат | новое (8 ноя) | Средний — снижает уверенность в регрессиях конкретно 3D |
| Крупный центральный `game.ts` (2036 строк) | архитектурный долг | Низкий при текущем темпе, но кандидат на разбиение при дальнейшем росте типов |
| Два параллельных поля приоритета | UX/данные | Низкий технически, повышает риск путаницы пользователя |
| Production Firebase никогда не проверялся вживую | методологическое ограничение | Контролируемо — следовать чек-листу `docs/FIREBASE.md` при желании закрыть |

Критических архитектурных рисков (P0-уровня: потеря данных, пробитие авторизации) **не обнаружено**. Инженерная дисциплина проекта (бюджеты, строгий TS, серверная валидация экономики, тесты правил) заметно выше типичного уровня для соло-проекта такого масштаба.
