# 08 — Дорожная карта дальнейшей разработки

Версия на момент аудита: 0.75.1. Структура этапов — по разделу 25 ТЗ, скорректирована с учётом того, что часть Этапа 2 и Этапа 4 уже фактически реализована (Planning System 2.0, 0.74.0–0.75.1, зависимости задач 0.75.0) — по прямому требованию ТЗ не планируется повторная разработка существующего.

## Этап 2. Основа планировщика — ЧАСТИЧНО ВЫПОЛНЕН

Выполнено: единый механизм задач (`Quest`), Inbox (локальный), планирование дня/недели/месяца (`TodayTasks`, `TasksCalendar`, `LifePlanMap`), канбан, матрица важно/срочно.

Остаётся:
- Квартальное и годовое планирование **вперёд** (не только отчёт).
- Мастер подтверждения недели (управляемый ритуал по образцу Sunsama, см. 07-COMPETITOR_COMPARISON.md).
- Расширенная модель повторений (N дней, дни месяца, ежегодно, конец серии, пропуски).
- Массовые операции и сохранённые фильтры.
- Drag-and-drop в канбане.

## Этап 3. Управление временем

Выполнено: календарь (день/неделя/2 недели/месяц), drag-and-drop переноса, изменение длительности, `PlanningSettings` (дневные минуты, резерв, лимиты, порог предупреждения о переносах).

Остаётся (это основной объём этапа):
- Time Blocking как отдельная сущность временного блока + проверка пересечений.
- Структурированная история переносов (дата → дата, причина, счётчик) — ключевая зависимость для анализа причин переносов и «Task Postponement Rate».
- Учёт дедлайнов — уже частично есть (`deadlineAt` отдельно от плановой даты), нужна явная карточка/напоминание о приближении.
- Режим фокуса на одну задачу (дёшево, высокий UX-эффект — см. 07).

## Этап 4. Управление проектами и целями — ЧАСТИЧНО ВЫПОЛНЕН

Выполнено: проекты (как Goal+Stages), этапы, зависимости задач с проверкой циклов (0.75.0), связи с картой пути (сферами), WOOP/если-то/контрольные точки.

Остаётся:
- Контроль неактивных/застрявших проектов (явный флаг «N дней без движения»).
- Гант на уровне этапов/задач с визуализацией критического пути (сейчас — только полосы и шкала сроков).
- Решить судьбу двух параллельных механизмов приоритета (объединить или явно развести в UI).

## Этап 5. Аналитика

Выполнено: `KeyResults`, месячный/годовой отчёты, история событий по сферам.

Остаётся (прямо зависит от Этапа 3):
- Фактическая нагрузка (нужен учёт фактического времени — отсутствует полностью, см. 04).
- Точность планирования (Plan Accuracy) как явная метрика.
- Переносы (аналитика) — зависит от истории переносов (Этап 3).
- Снимки планов (план на неделю/месяц «как было» для сравнения с фактом).

## Этап 6. Интеллектуальное планирование

Ничего не реализовано — весь этап впереди. Требует данных из Этапов 3 и 5 (факт времени, история переносов) как предпосылку — **нельзя начинать Этап 6 до завершения ключевых пунктов Этапа 3**, иначе рекомендации будут опираться на отсутствующие данные.

Рекомендуемый порядок внутри этапа:
1. Проверка нагрузки дня/недели (частично есть заготовка — `weekLoad`, `dailyMinutes`/`reservePercent`) — довести до видимого предупреждения в UI.
2. Выявление остановившихся проектов (не требует новых данных — можно сделать на основе `updatedAt`/последнего события проекта).
3. Поиск свободного времени — требует Time Blocking из Этапа 3.
4. Рекомендации по приоритетам/распределению — последними, как самые рискованные по непредсказуемости (см. предостережение про Motion в 07-COMPETITOR_COMPARISON.md: только предложения с подтверждением, без автоматического применения).

## Этап 7. Интеграции и оптимизация

Выполнено: TickTick (задачи + привычки через официальный MCP-сервер), 5-минутный авто-опрос.

Остаётся:
- Производственная (live) проверка TickTick и Firebase с реальным тестовым аккаунтом (чек-лист уже есть в `docs/FIREBASE.md`, не выполнялся).
- Напоминания/push-уведомления (сейчас только счётчик в колокольчике).
- Исправить нестабильный визуальный CI-тест 3D-комнат (`03-BUG_REPORT.md`, P2) — иначе дальнейшая 3D-оптимизация не будет иметь регрессионной защиты.
- Переподтвердить CSS-бюджет (AUD-009) перед следующим крупным визуальным изменением (канбан с drag-and-drop из Этапа 2 — хороший кандидат, где бюджет может быть пробит).
- Закрыть AUD-007 (потолок XP), если/когда появятся рейтинги игроков.

## Рекомендуемая последовательность разработки (сквозная, не по этапам ТЗ)

Между этапами есть зависимости, которые важнее номеров этапов:

1. **Сначала** — структурированная история переносов + учёт фактического времени (Этап 3 ключевое). Это фундамент почти для всей аналитики (Этап 5) и интеллектуального планирования (Этап 6).
2. **Параллельно, независимо** — drag-and-drop канбана, режим фокуса, расширенные повторения, мастер недели (всё — Этап 2/3, не имеют взаимных зависимостей, можно делать в любом порядке).
3. **После п.1** — метрики аналитики (Plan Accuracy, Postponement Rate, фактическая нагрузка).
4. **В последнюю очередь** — интеллектуальные рекомендации (Этап 6), т.к. зависят от накопленных данных п.1 и п.3; и Гант на уровне проектов (Этап 4 остаток) — наименее критично для «полноценного планировщика» по сравнению с остальным.
5. **Отдельно, не блокирует остальное** — live-проверка production Firebase/TickTick, починка визуального CI, бюджеты (Этап 7) — делать по мере необходимости, не являются зависимостью для нового функционала.

Если аудит покажет дополнительные уже готовые функции при следующей сверке — соответствующий пункт из этой карты снимается, как это уже произошло с Inbox/канбаном/зависимостями между аудитом от 7 ноября и этим.
