# 10 — Итоговая сводка для владельца проекта

Простым языком: что уже есть в PLAY YOUR LIFE, что хромает, и что делать дальше. Версия на момент аудита — 0.75.1. Подробности по каждому пункту — в документах 01–09 этой папки.

## Главный вывод

PLAY YOUR LIFE — это не сырой прототип, а зрелый, активно разрабатываемый продукт с хорошей инженерной дисциплиной (строгая типизация, бюджеты размера, серверная защита от накрутки наград, 500+ тестов). Большая часть того, что ты просил проверить, **уже реализована** — особенно свежая Planning System 2.0 (канбан, матрица важно/срочно, зависимости задач, настройки нагрузки) закрыла значительную часть разрыва с «полноценным планировщиком» буквально за последние 2 дня до этого аудита. Главные оставшиеся дыры — не в экранах, а в **данных, которых ещё нет**: нет учёта фактического времени и нет истории переносов, из-за чего невозможна часть аналитики и умных подсказок, которые ты описал в ТЗ.

## 20 важных проблем (найдено ровно столько, сколько подтвердилось — не дотягивал до 30 искусственно)

1. Структурированной истории переносов задач не существует — тянет за собой пробел в аналитике и умных подсказках.
2. Нет учёта фактического времени выполнения — та же причина.
3. Главная страница перегружена дублирующими блоками (TODO.md от 23.10, статус не переподтверждён).
4. Два параллельных механизма приоритета задачи (`priority` и важно/срочно) без явной связи.
5. Канбан «Мой план» меняет статус через выпадающий список, не перетаскиванием.
6. Удаление задачи не имеет восстановления/подтверждения с отменой.
7. `README.md` показывает версию 0.64.6 вместо 0.75.1.
8. `TODO.md` не актуализирован — риск повторной работы.
9. Визуальный CI-тест 3D-комнаты «Спорт» падает по таймауту скриншота.
10. CSS-бюджет был на 99% лимита на последнем измерении (0.73.x) — риск для следующего UI-патча.
11. Нет серверного потолка суммарного роста XP (AUD-007, станет важным при появлении рейтингов).
12. Нет массовых операций над задачами.
13. Нет сохранённых пользовательских фильтров.
14. Модель повторений ограничена 4 паттернами (нет «каждые N дней», конкретных дней месяца, ежегодных, конца серии).
15. Нет квартального/годового планирования вперёд (только годовой отчёт по факту).
16. Нет мастера подтверждения недели.
17. Нет проверки пересечений временных интервалов в календаре.
18. Нет контроля «застрявших» неактивных проектов.
19. Привычка не может быть привязана к проекту/цели.
20. Нет напоминаний (push/локальных) для задач и привычек.

## 20 самых полезных новых функций

1. Структурированная история переносов с причиной (фундамент для п.2–5 ниже).

11. Сохранённые фильтры/представления.
12. Квартальное и годовое планирование вперёд.
13. Явная сущность «временной блок» + проверка пересечений.

15. Напоминания для задач и привычек.
16. Привязка привычки к проекту/цели.
17. Выявление остановившихся проектов (на основе уже имеющихся данных — быстро реализуемо).
18. Поиск свободного времени в календаре.
19. Предложения по распределению нагрузки — **только с подтверждением пользователя**, без автоматики (урок из анализа конкурента Motion).

## Оптимальная структура меню (эволюционная, не замена)

Текущая структура в целом логична и не требует перестройки. Точечные изменения:

- Перенести блок аккаунта (почта/сохранение/выход) из каждой страницы → в «Профиль» (уже есть в бэклоге TODO.md).
- «Мои задачи» и «Мой план» сейчас выглядят как два соседних, концептуально близких раздела — рассмотреть объединение в единый раздел с вкладками (Сегодня / Входящие / Список / Календарь / Канбан / Матрица), чтобы не распылять внимание между двумя пунктами меню.
- Остальное менять не требуется.

## Рекомендованная архитектура планировщика

Менять не нужно — текущая архитектура (единый `GameState`, чистые функции-трансформеры, Firestore с ревизиями и слиянием конфликтов, `cloudSplit` для роста данных) уже спроектирована с запасом на рост. Единственное архитектурное решение, которое стоит принять осознанно сейчас, пока это дёшево: **формат будущей истории переносов** — предлагается хранить её как отдельный массив событий в `GameState` (по аналогии с уже существующим `Event`), а не раздувать сам объект `Quest`, чтобы не повторить проблему роста документа, которую уже один раз решали через `cloudSplit.ts`.

## Последовательность разработки

См. подробно `08-DEVELOPMENT_ROADMAP.md`. Коротко: сначала история переносов + факт времени (фундамент), параллельно — независимые UX-доработки (drag-and-drop, режим фокуса, повторения), затем аналитика поверх новых данных, и только в конце — умные рекомендации.

## Риски и зависимости

- Интеллектуальное планирование (Этап 6 ТЗ) **нельзя** начинать раньше истории переносов и факта времени — иначе рекомендации будут считаться по неполным данным.
- CSS-бюджет (99% на последнем замере) может заблокировать CI при следующем визуальном патче — проверить заранее.
- Production Firebase/TickTick ни разу не проверялись вживую за три аудита подряд — риск контролируемый (чек-лист есть в `docs/FIREBASE.md`), но стоит сделать это один раз на отдельном тестовом аккаунте, прежде чем сильно расширять синхронизацию.

## Что лучше сохранить без изменений

- Игровая экономика, система начисления XP/монет, правила `firestore.rules`.
- Карты пути/жизни (архитектура по сферам, а не по 3 отдельным измерениям) — решение уже осознанно принято ранее.
- Светлый игровой стиль и общая структура меню.
- Единая сущность Quest вместо раздельных «задача/мини-квест/бизнес-задание».
- Единая сущность «проект» (Goal+Stages) вместо отдельной сущности «Проект».
