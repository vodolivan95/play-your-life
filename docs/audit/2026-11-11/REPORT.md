Автоматические проверки охватывают доступные исходники через ESLint, TypeScript, сборку и существующие тесты. Проверка Python ограничена разбором AST; JSON — разбором формата. Ресурсы инвентаризированы, но каждый кадр спрайтов, модель и изображение вручную не исследованы. Старые документы не считаются доказательством текущей работоспособности. Для остальных модулей основное доказательство — автоматические тесты и браузерные сценарии; глубина проверки не равна построчному ревью.

## Стек и архитектура

React 19, TypeScript 5.9 (strict), Vite 7, Firebase Auth и Firestore. Клиент — SPA на статическом хостинге GitHub Pages. `AccountRoot.tsx` управляет входом и жизненным циклом аккаунта; `App.tsx` — навигацией, общим состоянием и экранами. Доменная логика — чистые функции над `GameState`.

Облачное сохранение: `AccountSave` → `firebaseSave` → Firestore. Есть локальные черновики, ревизии, трёхстороннее слияние, резервные копии; старые события и изображения вынесены в отдельные документы. Монеты защищены правилами и квитанциями однократных наград. XP и большинство пользовательских полей остаются клиентскими данными; это не серверный источник доверия для будущего общего рейтинга.

TickTick: Cloudflare Worker и отдельный Durable Object на аккаунт; OAuth-токены остаются на сервере. Firebase JWT проверяется по подписи, issuer/audience/срокам. OAuth state одноразовый и имеет срок; Origin ограничен. Вызовы provider API имеют таймауты; запросы аккаунта сериализованы. Для привычек — отдельная очередь и ограниченные повторные попытки. Проверки интеграции выполняются с имитацией провайдера.

3D: Three.js, React Three Fiber и drei; город и некоторые тяжёлые экраны загружаются лениво. Орфография: локальный worker nspell RU/EN. Самостоятельного SQL-сервера в проекте нет; SQL-инъекция как класс к этой архитектуре напрямую не относится.

## Реестр подтверждённых ошибок

### AUD26-001 — P2 — вложенные записи старого таймера не проверялись

- Место: `src/taskTimer.ts`, `readAll`, `activeTimer`, `elapsedSeconds`.
- Воспроизведение: записать в `play-your-life-task-timer-v1:<owner>` JSON `{"q":null}`; `isTimerStorageCorrupted` ранее возвращал false, `activeTimer` обращался к `null.runningSince`. Также принимались отрицательные секунды, неверные даты и несовпадающий taskId.
- Причина: проверялся только внешний объект, затем применялось приведение типа.
- Последствия: исключение или NaN при чтении/показе старой сессии, потеря возможности корректно учесть время.
- Исправление: проверка каждой записи, конечности/неотрицательности секунд, даты, actionId и совпадения ID. Исходный JSON чтением не перезаписывается; срабатывает существующее предупреждение о повреждении.
- Регрессия: новый тест с шестью повреждёнными вариантами; до правки — ошибка, после — успех.

### AUD26-002 — P2 — свойства прототипа воспринимались как таймер

- Место: `src/taskTimer.ts`, `readTimer` и внутренний словарь.
- Воспроизведение: `readTimer('prototype-owner', 'toString')` на пустом хранилище возвращал функцию вместо undefined; `__proto__` — объект прототипа.
- Причина: обычный объект `{}` и индексный доступ без проверки собственного ключа.
- Последствия: неверный тип таймера при специальных ID, возможное некорректное вычисление времени. Это ошибка локальной обработки ключей; удалённое исполнение кода или доступ к чужим данным не доказаны.
- Исправление: словарь без прототипа и `Object.hasOwn` при чтении.
- Регрессия: оба специальных ключа проверены; до правки тест падал, после проходит.

### AUD26-003 — P2 — повторный старт старого таймера обнулял время

- Место: `src/taskTimer.ts`, `startTimer`.
- Воспроизведение: старт q в 10:00, повторный старт q в 10:05, завершение в 10:06. Ранее возвращалось 60 секунд вместо 360, менялся actionId; пауза также могла быть перезаписана новым стартом.
- Причина: защита проверяла другой активный таймер, а тот же ID перезаписывался.
- Последствия: потеря накопленного времени и устойчивого ключа события. В текущем интерфейсе новые сессии уже используют Focus Tracking; область ошибки — совместимый API старого таймера.
- Исправление: повторный start возвращает существующую сессию; продолжение после паузы остаётся отдельной операцией resume.
- Регрессия: запуск/повтор/пауза/повтор; до исправления — ошибка, после — успех.

### AUD26-004 — P2 — финансовая операция могла стать несохраняемой

- Место: `src/finance.ts`, `validInput`, `addTransaction`, `updateTransaction`.
- Воспроизведение: добавить или изменить операцию с `amount: 0.001`. Вход проходил `amount > 0`, затем сумма округлялась до `0`, а `validFinanceTransactions` требовал положительную сумму.
- Причина: входная проверка и сохранённое представление использовали разную точность.
- Последствия: GameState с нулевой финансовой операцией отклоняется при облачном сохранении/восстановлении.
- Исправление: проверяется положительность суммы после округления до копеек. Формат хранения и правила округления остальных сумм сохранены.
- Регрессия: создание и обновление отклоняют 0.001, сумма 0.01 сохраняется и проходит валидатор; до правки — ошибка, после — успех.

### AUD26-009 — P3 — финансовая дата проверяется по форме, открыто

- Место: `src/finance.ts`, `validInput`, `validFinanceTransactions` (аналогичный подход у даты платежа).

### AUD26-010 — P2 — тест города запрещал штатное снижение качества AUTO

## Безопасность и целостность

- Firestore: owner-проверки на `players/{uid}` и вложенные документы; listing запрещён, revision монотонная, монеты ограничены подтверждёнными наградами. Статический анализ не заменяет эмулятор и сверку опубликованных правил.
- Пароли обрабатывает Firebase Auth; клиент не хранит собственную парольную базу. Конфигурация Firebase в браузере публичная и сама по себе не является секретным ключом администратора.
- JWT worker проверяет RS256 и подпись по публичному JWK, issuer/audience, exp/iat/auth_time и sub. Серверные OAuth-токены не включаются в клиентские настройки.
- OAuth state имеет nonce, срок и удаляется при callback; API использует Bearer и проверку Origin. Это не cookie-сессия приложения, классическая CSRF-модель требует учёта этой архитектуры.
- В исходниках src/integrations не найдены `eval`, `new Function`, `innerHTML` и `dangerouslySetInnerHTML`; React-текст экранируется. Это ограниченный поиск потенциальных sinks, а не формальное доказательство отсутствия XSS.
- Загрузка изображений ограничена размером и преобразуется Canvas в растр; копии проверяются по формату, размеру и схеме. SSRF-подобные пользовательские URL не используются для server fetch: адреса провайдера фиксированы; MCP URL — серверная конфигурация.
- Quality gate сканирует отслеживаемые текстовые файлы на распространённые секреты и запрещённые .env/архивы. Приватные ключи в текущем проверенном дереве этим способом не обнаружены. Полный secret scan истории и всех форматов не выполнен.

Оставшиеся риски, которые не выдаются за воспроизведённые атаки:

1. `worker.ts:body` проверяет лимит после `request.text()`; для защиты памяти целесообразно ограничить поток до полного чтения. Троттлинг привычек не заменяет общий лимит всех маршрутов/неавторизованных запросов; внешние Cloudflare/WAF-настройки недоступны.
2. `firebaseSave.ts` удаляет неиспользуемые изображения после транзакции. Параллельное возвращение старой обложки другим устройством между commit и delete требует отдельного интеграционного теста; воспроизведение потери здесь не выполнено. Рекомендация — отложенная сборка мусора с проверкой актуальных ссылок.
3. `taskTimer.ts:writeAll` подавляет ошибку localStorage, хотя обещанный в комментарии полноценный резерв в памяти не реализован. В текущем UI это путь совместимости старых сессий. Для него нужны явный статус записи и отдельный сценарий исчерпания квоты; общий механизм новых focus-сессий хранится в GameState.
4. В `TaskPlanningFields.apply` и `FocusSection.run` пробная операция на текущем props-state не доказывает успех следующего updater на более свежем state. Для гостевого React-dispatch возможна задержка; необходим тест конкурентного изменения/удаления задачи. В аккаунтном адаптере updater вызывается синхронно, что сужает риск.
5. Регистрация, обновление displayName и первичная загрузка аккаунта асинхронны; сценарий сбоя `updateProfile` после успешного создания пользователя требует Auth emulator E2E.

## Производительность и архитектурные рекомендации

Фактический вес сборки измерен штатным `check:budgets`; результаты приведены ниже. На исходной версии начальный JS был близок к пределу 464 КиБ gzip. В объединённом main 0.80.1 уже реализована ленивая загрузка разделов и снижены стартовые бюджеты до 420/70 КиБ — это изменение других PR, сохранённое при интеграции. Не поднимать бюджет автоматически: кандидат на следующий этап — lazy-loading крупных редко используемых экранов и локализация их CSS после измерения эффекта.

AST-инвентаризация локальных import/export и динамических import: 215 TS/TSX-узлов, 675 рёбер; 194 достижимы из `main.tsx`, явных неразрешённых относительных импортов с расширением TS не найдено. Это не полный bundler-граф: worker через `new URL`, декларации типов и тестовые/демо-точки входа требуют отдельного учёта. Недостижимость в этом графе не доказывает, что файл можно удалить.

`App.tsx` объединяет навигацию, корневое состояние, модальные действия и экраны; `game.ts` — большая доменная модель; `stateValidation.ts` — центральная проверка. Это повышает стоимость изменения и риск циклических импортов. Разделять постепенно по доменам с сохранением экспортов и регрессий; масштабный рефакторинг в этот патч не включён.

Рост одного Firestore-документа остаётся системным ограничением: economyRecords, привычки и финансовые операции растут, хотя история/картинки уже разделены. Есть защитный лимит документа и понятная ошибка. Следующий этап — проектирование архивирования/пагинации с сохранением доказательств однократных наград; текущие записи нельзя просто обрезать.

`stateMerge.ts:mergeSetArray` использует вложенный поиск с canonical-сериализацией; при больших массивных полях без ID возможна квадратичная стоимость. Рекомендация — Map/Set по заранее рассчитанным ключам после замера на реалистичных данных. Это потенциальное узкое место, а не измеренная задержка UI этого прогона.

Реальное время API, p95/p99, FPS настоящего телефона, долгие утечки памяти и нагрузка конкурентных пользователей не измерены. Производительность production по одним размерам сборки не оценивается.
