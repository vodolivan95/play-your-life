## 1. Решения пользователя и границы

Пользователь подтвердил: отдельные «Цели» пока не выделять, это проекты. Рабочая структура: **Сфера → Проект → Этап → Задача → Подзадача**. Проект без этапов и самостоятельная задача допускаются. Требования раздела 14 исходного ТЗ относятся к существующему проекту: измеримый результат, текущий/целевой показатель, способ расчёта прогресса, этапы и история. Поле «Связанная цель» из раздела 10 исключается. Поиск, Inbox, аналитика и обзоры содержат одну сущность «Проект».

`Goal`, `state.goals`, `goalId` остаются внутренними именами для совместимости. Проект уже существует; новые таблицы или параллельное хранилище проектов не создавать. Упоминания «прогресс целей» в исходнике означают прогресс проектов. Вложенные проекты не вводятся этим уточнением.

Существующие светлая и тёмная темы, игровой город, карты пути, уровни, XP и лайфкоины сохраняются. Раздел 28 исходника не означает отказ от тёмной темы или замену согласованных экранов. Список пожеланий исходника не является подтверждением отсутствия этих функций в приложении.

## 2. Пользователи, данные и навигация

Работать в текущей модели владельца аккаунта, локального режима и демоигры. Новые административные роли не нужны. Пользователь видит и изменяет только свои данные; сервер проверяет владельца независимо от UI. Демо работает с отдельным набором примеров, личный профиль — с реальными данными.

Использовать «Мои задачи» для списка, календаря, входящих и планирования. «План жизни» остаётся обзором по сферам и периодам. «Проекты» содержит существующее рабочее пространство проекта. «Привычки» остаётся отдельным разделом. Аналитика расширяет «Ключевые итоги». Параллельный верхнеуровневый раздел с копиями задач не создавать.

В «Моих задачах» развить переключение «Сегодня / Завтра / Неделя / Месяц / Все задачи» внутри существующего пространства, сохранив доступ к календарю, входящим и плану жизни. Окончательный состав вкладок согласовать с текущими сценариями, не увеличивая число пунктов основного меню.

## 3. День, задачи и входящие — разделы 4, 15, 16, 19, 20 исходника

**Куда добавить:** «Мои задачи → Сегодня», над списком и в существующем `TaskWindow`. Источник — `state.quests`, существующие привычки и журнал наград.

- Сводка дня: задачи, выполнено, процент, просроченные; время показывать с покрытием оценками («2 ч, ещё 3 задачи без оценки»). Отсутствующая оценка не равна нулевой длительности.
- Группы: главные, назначенные по времени, остальные, привычки, выполненные; просроченные доступны отдельно. Закрепление `pinned` уже работает и не должно молча стать ограниченной дневной отметкой. Для главных задач нужен отдельный дневной выбор, рекомендуемое число 3 с настройкой.
- Быстрое добавление: достаточно названия. Использовать текущую форму и её значения по умолчанию; проект, этап, дата и дополнительные поля необязательны. Для будущего универсального Inbox определить явное состояние «разобрано»: задача без срока может быть сознательно запланированной без даты и не обязана оставаться во входящих.
- Входящие объединяют локальные неразобранные задачи и существующий импорт TickTick. Импортируемая карточка не становится второй локальной задачей: сначала разбор, затем существующая связь внешнего и локального ID. Без TickTick локальные входящие доступны.
- Действия карточки: назначить дату, выбрать проект/этап, изменить приоритет, подзадачи, выполнить, архивировать, удалить с подтверждением. Возврат во входящие снимает признак разбора; очищение времени должно быть явным. «Не буду делать» сохраняет задачу и её историю, исключает из активной нагрузки, не начисляет наград.
- Поиск/сортировка и массовое выделение работают по ID. Перед массовой операцией показывать количество и новое значение; несовместимые операции явно отмечать. Завершение и отмена выполнения используют существующие бизнес-функции и защиту от повторной награды.
- Приоритет расширить с `low/normal/high` до четырёх уровней совместимым способом. `importance` и пользовательская срочность независимы от приоритета и вычисленной просрочки. Матрица — представление тех же задач.
- «Начать день»: необязательный мастер с оставшимися задачами, дневным фокусом, доступным временем и конфликтами; изменение сохраняется после подтверждения. «Завершить день»: реальные итоги и поштучный разбор остатка. Автопереноса на завтра нет.

**Приёмка:** задача создаётся с названием, после перезагрузки доступна по тому же ID; перенос обновляет календарь и карточку; отмена выполнения не начисляет XP повторно; массовая операция не затрагивает скрытые невыбранные задачи; отказ от мастера оставляет данные как были.

## 4. Неделя и месяц — разделы 5–6

**Куда добавить:** «Мои задачи → Неделя/Месяц», на базе `TasksCalendar` и существующего `LifePlanner`. Недельный список и календарь используют одинаковые даты и фильтры.

Мастер «Спланировать неделю»: остаток → активные проекты → приоритеты → доступное время → распределение → проверка нагрузки → подтверждение. До последнего шага это черновик; закрытие не переносит задачи. Показывать семь дней, плановые минуты, выполнения и остаток. Перетаскивание имеет кнопку-альтернативу для телефона и клавиатуры. Копирование недели создаёт предварительный список с выбором: уже существующие экземпляры повторений не дублируются.

Месяц показывает задачи, сроки этапов, дедлайны и временные блоки. Создание из ячейки подставляет дату, сохраняет обычную задачу. Результаты месяца опираются на существующий `monthlyFocus` (сейчас до трёх проектов). Требование 3–5 из исходника не меняет этот лимит автоматически: расширение отдельно описать и проверить везде, где используется monthlyFocus. Прогресс открывает исходный проект.

**Приёмка:** предложенный недельный план до подтверждения не меняет даты; подтверждение переносит только выбранные задачи; повторное подтверждение не создаёт копий. Месяц/неделя показывают одну задачу с тем же ID и обновляют её одновременно.

## 5. Время, переносы и повторения — разделы 7–9, 17

**Куда добавить:** `TaskWindow`, «Мои задачи → Календарь», настройки планирования в профиле. Повторно использовать `estimateMinutes`; не добавлять конкурирующее `estimatedMinutes`.

Плановая дата `dueAt` и начало `startsAt` уже синхронизируются с TickTick. `deadlineAt` — отдельный локальный дедлайн. Новые временные блоки ссылаются на ID задачи и дают возможность нескольким сеансам работы над одной задачей. Отдельные события календаря не создают игровые задачи и награды. Дедлайн не сдвигается вместе с планом без отдельного действия.

Настройки: часовой пояс, рабочие дни/выходные, интервалы доступности, исключения на конкретную дату, резерв времени, лимит главных задач, порог предупреждения о переносах и WIP. Даты без времени хранятся как `YYYY-MM-DD`; моменты — ISO. Старые данные продолжают читаться в существующей локальной модели. При изменении зоны показывать влияние на расписание; голые даты не сдвигать.

Оценка: 5/15/30/45/60/90 минут и своё значение. Фактические интервалы записывать вручную или таймером; перезагрузка не должна терять начатый сеанс. Одновременно работающий таймер учитывать в модели конфликта нескольких устройств. Не вычислять факт из планового интервала.

История переносов фиксирует ID события, ID задачи, момент, старую/новую плановую дату и необязательную причину. Причины — из исходного ТЗ, произвольная ограниченная заметка для «Другая». Первое назначение даты отдельно от переноса; изменение только часа внутри дня отдельно от смены дня. Повторный запрос одного действия не создаёт два события. Новый экземпляр повторения не наследует историю прежнего. История видна после выполнения и в «Активности» задачи.

При достижении порога показывать число переносов и действия: подзадачи, уменьшить объём, выделить время, сменить приоритет, отложить, удалить. Предупреждение не блокирует сохранение. В календаре конфликт интервалов даёт список пересекающихся задач и свободные варианты; пользователь может разрешить пересечение. Время свободного окна считается по объединению занятых интервалов, пересечения не вычитаются дважды.

Повторения расширить шаблоном серии и экземплярами: по выходным, выбранные дни, N дней, ежегодно, от завершения, конец по дате/числу. Существующие четыре варианта сохранить. Действия «Этот экземпляр / Будущие / Вся серия» показывают область до записи. ID экземпляра стабилен для пары серия+плановое вхождение; пропуск и перенос не создают вторую награду. Политику конца месяца (31-е число) определить явно: текущая реализация допускает переход в март, это уже закреплено тестом и требует осознанного изменения.

**Приёмка:** перенос сохраняет старую и новую дату, не меняет дедлайн; после перезагрузки история и таймер восстанавливаются; конфликт не вызывает скрытый перенос; смена зоны и DST проверены; повторная доставка изменения не удваивает историю, экземпляры и награды.

## 6. Проекты и привычки — разделы 10–14, 18

**Куда добавить:** существующий `GoalWorkspace`, список проектов, существующая страница привычек. Сохранить текущие паузу, этапы, контрольные точки, результат, WOOP, «Если–То», фокус недели, заметки, историю и награды.

Канбан: запланировано / к выполнению / в работе / ожидает / завершено. Статусы — дополнительный рабочий процесс той же задачи, завершение вызывает существующую функцию. `done` остаётся совместимым отражением завершения. При выходе из «Завершено» применять текущую отмену, без повторной награды. Лимит WIP предупреждает, не теряет карточки. Фильтры: проект, сфера, приоритет, завершённые.

Гант дополняет существующие полосы этапов: реальные задачи, зависимости, контрольные точки, прогресс; перенос показывает затронутые элементы. Для зависимостей проверять существование узлов, владение и циклы. Каскадное изменение сроков — отдельный предпросмотр и подтверждение. Таблица и таймлайн открывают тот же `TaskWindow`.

Контроль завершения: следующие действия, просрочка, отсутствие активности, риск дедлайна и изменение плана. Сигнал строится по конкретным датам и событиям и открывает проект/задачу. Порог неактивности должен быть настройкой, пример «12 дней» не константа. Без истории активности показывать недостаточность данных. Материалы проекта начинают со ссылок; загрузка файлов требует отдельной инфраструктуры и лимитов.

Привычки сохраняют свою сущность и историю отметок. Повторяющаяся задача не становится привычкой. Связь привычки с проектом должна быть необязательной; существующие серии и награды не пересчитывать задним числом. График, пропуск и напоминания учитывают пояс привычки.

**Приёмка:** открытие одной задачи из списка, канбана и календаря ведёт к одному ID; циклическая зависимость отклоняется до записи; каскад отменяется без изменений; привычка работает без связанного проекта; старые проекты открываются без заполнения новых полей.

## 7. Обзоры, аналитика, рекомендации — разделы 21–23, 25

**Куда добавить:** недельный обзор в «Ключевых итогах» и объяснимые подсказки рядом с планом. Все карточки имеют переход в исходный список с тем же периодом.

Формулы:

- выполнено за период — задачи `done` с локальным днём `completedAt` внутри обеих границ; это текущий статус, исторические повторные отметки считать по отдельному журналу;
- процент исполнения плана — выполненные ID из подтверждённого снимка плана / все ID снимка; без снимка не называть текущее отношение задач исторической точностью плана;
- задачи с переносом — уникальные taskId событий изменения дня за период; число событий показывать отдельно;
- среднее переносов — число событий переноса / число уникальных перенесённых задач, при пустом знаменателе «Нет данных»;
- плановое время — сумма оценок выбранного плана, отдельно число задач без оценки;
- фактическое время — сумма проверенных рабочих сеансов, исключая дубли событий;
- коэффициент оценки — сумма факта / сумма плана только по сопоставимым завершённым задачам с обеими оценками и положительным планом; показывать размер выборки;
- свободное время — доступные интервалы минус объединение занятых интервалов и резерв;
- перегрузка — сумма оценок незавершённых задач сверх доступного бюджета; задачи без оценки означают неполную оценку риска;
- прогресс проекта — существующий выбранный режим `goalProgressValue`; среднее процентов разных проектов не выдавать за объективный прогресс сферы;
- заработано — журнал начислений, а не повторное вычисление награды из изменяемой карточки задачи.

Недельный обзор: план/факт задач и времени, привычки, проекты, дни активности, просрочка и переносы. Графики дней/недель/месяцев используют одинаковые определения. Прошлая история переносов и времени до внедрения журналов недоступна — не восстанавливать её догадками.

Рекомендации первого этапа детерминированные: перегрузка, свободные окна, забытые задачи, отсутствие следующего шага, приближение срока. Каждая показывает факт, формулу/основание, период, источник и действие. Предложение плана не записывается до подтверждения; платный AI API не подключать. Декомпозиция — пользовательские подзадачи и шаблоны.

## 8. Интеграции, поиск и уведомления — разделы 24, 26–27

Расширять текущую интеграцию TickTick. Проверять OAuth, обновление токена, сопоставления, обмен полями, выполнение/отмену, конфликты, массовые удаления, offline и отключение. Для каждого нового поля описывать: передаётся официальным API / хранится только локально / ограничение. Текущий обмен переводит три приоритета в 1/3/5; P1/P2 не должны молча потерять различие. Реальные интеграционные проверки отделять от mock. Проект и этап не становятся удалёнными проектами TickTick автоматически.

Глобальный поиск расширяет существующий `searchEverything`: добавить этапы, привычки и заметки, сохранить переходы к задачам/проектам/сферам. Фильтры и сохранённые представления принадлежат аккаунту, не содержат копии задач; переименование/удаление объекта не ломает загрузку фильтра. На телефоне фильтры доступны отдельной панелью.

Центр уведомлений расширяет текущий колокольчик. Для дедлайнов, начала задачи, привычек, неактивных проектов и обзоров задавать канал, время, частоту, тихие часы и ссылку на источник. Стабильный ключ события предотвращает повторный показ; прочтение не меняет задачу. Разрешение браузера запрашивается действием пользователя. Закрытая вкладка требует push-инфраструктуры; обычный таймер работает только при доступном приложении. В отсутствие подключения показывать состояние и действие настройки.

## 9. Архитектура, миграция и безопасность — разделы 29–33

Предложение следующего этапа для отдельного согласования по AGENTS.md:

1. Опциональные поля задачи: рабочий статус, расширенный приоритет, важность, пользовательская срочность, признак разбора, время архивации, связи зависимостей, ID серии/экземпляра. Существующие названия `startsAt`, `dueAt`, `deadlineAt`, `estimateMinutes` переиспользуются.
2. Отдельные журналы: переносы и сеансы времени. Отдельные сущности: блоки календаря, события без задач, шаблоны повторения, снимки подтверждённых дневных/недельных планов, пользовательские настройки и сохранённые фильтры. Каждой записи назначать владельца, стабильный ID, timestamp и версию; избегать неограниченного роста основного Firestore-документа, учесть текущую архивацию истории.
3. Единственный слой команд задачи применяется ко всем UI и адаптеру интеграции. Команда сначала валидирует итоговую сущность и зависимости, затем атомарно меняет состояние и журнал. UI не ведёт параллельную копию данных.
4. Миграция читает старые поля, добавляет значения только при необходимости, не изобретает историю. Старый `done` и `rewardClaimed` остаются совместимыми. Перед обновлением резервная копия проходит валидацию; миграция повторяемая, тестируется на старых fixture. Для отката описать, как старая версия обработает неизвестные поля; если безопасное редактирование невозможно, блокировать старый клиент, сохраняя экспорт.
5. Новые поля проходят stateValidation, round-trip backup, merge двух клиентов, разделение документов и Firestore Rules при хранении в новых коллекциях. Проверить конфликты параллельных переносов/таймеров/серий и изоляцию аккаунтов.
6. Награды идут через существующий журнал; структуру экономики не менять. Значительные изменения оформляются в Issue до реализации и согласуются с Иваном. Автоматическое слияние в main не разрешено текущим поручением.

## 10. Проверки и этапы — разделы 34–39

Этап A: актуальный код, инвентаризация, воспроизводимые ошибки и минимальные исправления без миграции. Этап B: согласованная модель и команды, совместимость старых сохранений. Этап C: день/Inbox/массовые действия/повторения. Этап D: неделя, доступность, блоки, история переносов и время. Этап E: канбан, зависимости, Гант и завершение проектов. Этап F: обзоры, аналитика и рекомендации. Этап G: уведомления, поиск, PWA, реальные интеграционные проверки и оптимизация.

На каждом этапе: `npm run check`, `npm test`, бюджеты сборки, релевантные браузерные сценарии desktop/mobile, затем GitHub Actions для конкретного коммита и второе ревью. Нельзя объявлять весь проект завершённым по наличию интерфейса.

Сохранить все 50 сценариев исходника: создать/изменить/перенести/завершить/отменить/удалить/восстановить (если поддержано)/дублировать/подзадача/приоритет; календарь и DST; проекты и связи; сохранение/offline/два клиента/backup; TickTick и однократные награды. Дополнительно проверить ночные выполнения в Europe/Moscow, конец недели, атомарное изменение интервала, задачи «Не буду делать», циклы зависимостей, одновременные таймеры, повторное подтверждение мастера и длинную историю.

Проверить PWA manifest, иконки, обновление и offline на реальном браузере; наличие manifest само по себе не доказывает offline.
