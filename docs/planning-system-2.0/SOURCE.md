# ЧАСТЬ II. НОВАЯ АРХИТЕКТУРА ПЛАНИРОВАНИЯ

## 3. Единая система данных

Основная проблема, которую необходимо исключить, — разрозненность информации.

Сейчас и в дальнейшем пользователь должен работать с единой системой.

Предлагаемая структура:

**Сфера жизни → Цель → Проект → Этап → Задача → Подзадача.**

При этом структура должна оставаться гибкой.

Допускаются:

- Задачи без целей.
- Проекты без долгосрочной цели.
- Цели без проектов.
- Задачи, непосредственно связанные с целью.
- Этапы, содержащие несколько задач.
- Повторяющиеся задачи.
- Личные задачи без игровых наград.

Важно сохранить совместимость с существующими данными.

### Пример

Сфера: Саморазвитие.

Цель: Выучить английский до уровня B2.

Проект: Подготовка к B2.

Этап: Освоить грамматику.

Задачи:

- Пройти урок.
- Выполнить упражнения.
- Повторить 20 слов.
- Посмотреть видео на английском.

Подзадачи могут существовать внутри каждой задачи.

### Сквозное обновление данных

Если пользователь выполняет задачу, автоматически должны обновляться:

1. Статус задачи.
2. Прогресс этапа.
3. Прогресс проекта.
4. Прогресс цели.
5. Прогресс сферы жизни.
6. Выполнение дневного плана.
7. Статистика недели.
8. Статистика месяца.
9. Игровые награды, если они предусмотрены.
10. Связанные календарные представления.

Расчёты должны происходить на основе реальных данных.

## 4. Раздел «Мой план»

Нужно проверить, существует ли сейчас полноценный планировщик.

Если функциональность отсутствует или реализована частично, необходимо её доработать.

Предлагаемая структура:

**Мой план**

Вкладки:

- Сегодня.
- Завтра.
- Неделя.
- Месяц.
- Все задачи.

Пользователь должен иметь возможность переключаться между ними без перезагрузки приложения.

## 4.1. План на сегодня

Экран должен содержать:

**Верхний блок**

- Текущая дата.
- Количество запланированных задач.
- Количество выполненных задач.
- Процент выполнения.
- Суммарная плановая нагрузка.
- Оставшееся запланированное время.
- Количество просроченных задач.

**Основной блок**

Задачи дня, разбитые на категории:

1. Главные задачи.
2. Запланированные по времени.
3. Остальные задачи.
4. Привычки.
5. Выполненные.

Пользователь должен самостоятельно выбирать главные задачи дня.

Рекомендуемое количество — три.

Ограничение должно быть настраиваемым.

## 4.2. Управление задачами

Реализовать:

- Быстрое создание.
- Редактирование.
- Удаление.
- Дублирование.
- Перенос.
- Изменение приоритета.
- Выполнение.
- Отмену выполнения.
- Архивацию.
- Массовое выделение.
- Массовый перенос.
- Массовое изменение приоритетов.
- Массовое завершение.
- Поиск.
- Фильтрацию.
- Сортировку.

Все действия должны немедленно отображаться в интерфейсе.

При ошибках сохранения необходимо явно сообщать пользователю о проблеме.

## 4.3. Быстрое создание задачи

Добавить компактную форму.

Дополнительные поля:

# ЧАСТЬ IV. ПЛАНИРОВАНИЕ НЕДЕЛИ

## 5. Полноценный недельный планировщик

Создать удобную систему недельного планирования.

Пользователь должен видеть всю неделю.

Предусмотреть два режима.

### Режим 1. Список

Понедельник — воскресенье.

В каждом дне:

- Количество задач.
- Главные задачи.
- Плановая продолжительность.
- Выполненные задачи.
- Оставшиеся задачи.

### Режим 2. Календарь

Семь колонок.

Задачи отображаются внутри соответствующих дней.

Поддержать перетаскивание задач между днями.

### Дополнительные функции

1. Перенос задачи на другую дату.
2. Изменение времени выполнения.
3. Копирование плана предыдущей недели.
4. Создание повторяющегося недельного расписания.
5. Отображение свободного времени.
6. Распределение задач по дням.
7. Просмотр нагрузки.
8. Выделение перегруженных дней.
9. Перенос нескольких задач одновременно.
10. Сравнение запланированного и выполненного.

### Важная функция

**«Спланировать неделю»**

При нажатии открывается мастер планирования.

Шаги:

1. Посмотреть незавершённые задачи.
2. Посмотреть активные цели.
3. Выбрать приоритеты недели.
4. Определить доступное время.
5. Распределить задачи.
6. Проверить загрузку.
7. Подтвердить план.

После подтверждения появляется реальное недельное расписание.

Необходимо проверить существующий календарь и превратить его в рабочий инструмент планирования времени.

Поддержать виды:

- День.
- Неделя.
- Месяц.
- Список событий.

### Основные функции

1. Создание задачи непосредственно в календаре.
2. Изменение времени перетаскиванием.
3. Изменение продолжительности.
4. Перенос между днями.
5. Просмотр пересечений.
6. Отображение свободных интервалов.
7. Создание событий без задач.
8. Повторяющиеся события.
9. Напоминания.
10. Настройка рабочего времени.
11. Настройка выходных.
12. Настройка личного расписания.

## 7.1. Time Blocking

Добавить механизм блокировки времени.

Пользователь сможет распределять задачи по временным интервалам.

Пример:

09:00–10:00 — Английский.

10:00–11:30 — Работа над проектом.

12:00–13:00 — Спорт.

15:00–16:00 — Личные задачи.

Задача должна сохранять связь со своим временным блоком.

Если время изменилось, календарь обновляется.

## 7.2. Проверка пересечений

Если пользователь назначает две задачи на одно время, система показывает предупреждение.

Предусмотреть:

- Отображение конфликта.
- Предложение свободного интервала.
- Возможность разрешить пересечение вручную.

Запрещать пересечения безусловно не нужно.

Некоторые события могут выполняться параллельно.

# ЧАСТЬ VII. БОРЬБА С БЕСКОНЕЧНЫМИ ПЕРЕНОСАМИ

## 8. Контроль переносов задач

Это один из самых важных модулей.

Пользователь не должен бесконечно переносить задачи, создавая иллюзию продуктивности.

### 8.1. История переносов

Для каждой задачи сохранять:

- Первоначальную плановую дату.
- Текущую плановую дату.
- Количество переносов.
- Даты переносов.
- Предыдущие значения.
- Причину переноса, если пользователь её указал.

История должна сохраняться даже после выполнения задачи.

### 8.2. Контроль повторных переносов

Если задача переносится несколько раз, показывать предупреждение.

Например:

«Эта задача переносилась уже три раза. Возможно, стоит изменить подход к её выполнению».

Предложить действия:

- Разбить на подзадачи.
- Уменьшить объём.
- Выделить отдельное время.
- Пересмотреть приоритет.
- Отложить до конкретной даты.
- Удалить неактуальную задачу.

Количество переносов, после которого появляется предупреждение, должно настраиваться.

### 8.3. Причины переносов

Предусмотреть варианты:

- Не хватило времени.
- Изменились приоритеты.
- Не хватает информации.
- Задача слишком сложная.
- Появилась срочная работа.
- Потеряла актуальность.
- Другая причина.

Не требовать объяснения при каждом переносе.

### 8.4. Аналитика переносов

Показывать:

- Количество перенесённых задач.
- Долю перенесённых задач.
- Среднее количество переносов.
- Задачи с наибольшим числом переносов.
- Причины переносов.
- Динамику по неделям.

### 8.5. Контроль перегрузки

Перед подтверждением нового плана система должна сравнивать его с доступным временем.

Если пользователь пытается запланировать 12 часов задач на день с 5 свободными часами, необходимо показать предупреждение.

Предложить сократить или перераспределить нагрузку.

# ЧАСТЬ VIII. РЕАЛИСТИЧНОЕ ПЛАНИРОВАНИЕ

## 9. Учёт продолжительности задач

Добавить или проверить поле:

**Плановая продолжительность.**

Варианты быстрого выбора:

- 5 минут.
- 15 минут.
- 30 минут.
- 45 минут.
- 60 минут.
- 90 минут.
- Своя продолжительность.

### 9.1. Фактическое время

Пользователь должен иметь возможность указать время, реально потраченное на задачу.

Возможные способы:

1. Ручной ввод.
2. Таймер.
3. Отметка времени начала и завершения.

### 9.2. Анализ точности планирования

Сравнивать:

Плановое время / Фактическое время.

Пример:

Планировалось: 30 минут.

Фактически: 55 минут.

Отклонение: +25 минут.

На основе истории система может рекомендовать более реалистичную оценку.

### 9.3. Коэффициент планирования

Рассчитывать отношение фактически затраченного времени к запланированному.

Использовать историю сопоставимых задач.

Если пользователь регулярно недооценивает продолжительность определённого типа задач, система предлагает увеличить плановое время.

Рекомендация должна быть объяснимой.

# ЧАСТЬ XI. ДИАГРАММА ГАНТА

## 12. Визуальный план проекта

Реализовать диаграмму Ганта для проектов, где она действительно полезна.

На диаграмме должны отображаться:

- Этапы.
- Задачи.
- Даты начала.
- Даты завершения.
- Зависимости.
- Контрольные точки.
- Процент выполнения.

Поддержать изменение сроков перетаскиванием.

### Зависимости задач

Например:

Задача Б начинается после завершения задачи А.

При переносе задачи А система предупреждает о влиянии на зависимые задачи.

Автоматический перенос зависимых задач должен быть отдельной подтверждаемой операцией.

Нельзя незаметно менять согласованный план.
