## 1. Счётчик и история переносов (раздел 4 ТЗ)

- `recordTaskSchedule()` переписан: классифицирует изменение даты задачи как `schedule` (первое назначение/снятие даты — не перенос), `reschedule` (сменился день) или `retime` (день тот же, другое время), вычисляет направление переноса.

- Мягкая подсказка при достижении `moveWarning` переносов — 5 вариантов (уменьшить объём, разбить на подзадачи, назначить конкретное время, пересмотреть приоритет, проверить актуальность). Это текст, не игровой штраф: XP, монеты и прогресс не меняются.

## 3. Аналитика переносов (раздел 6)

`postponementAnalytics(state, now?, questIds?)` возвращает: `totalMoves`, `tasksWithMoves`, `movesThisWeek`/`movesThisMonth`, `forwardMoves`/`backwardMoves`, `averagePerTask`, `mostPostponed`, `top10`, `postponementRate`, `insufficientData`.

**Formula — Task Postponement Rate**: доля задач с известной плановой датой, перенесённых *вперёд* хотя бы один раз:

```
postponementRate = |{задачи с ≥1 переносом вперёд}| / |{задачи, у которых когда-либо была плановая дата}|
```

Переносы назад не увеличивают числитель (раздел 6.4 ТЗ: «назад» — это не откладывание). Пока задач с известной плановой датой меньше `MIN_SCHEDULED_FOR_RATE = 5`, функция возвращает `insufficientData: true` и `postponementRate: undefined` — интерфейс показывает «Недостаточно данных» вместо вводящего в заблуждение процента на почти пустой истории.

`monthlyMoves(state, month)`/`monthlyActualMinutes(state, month)` — те же данные, отфильтрованные по дате самого события (не по дате задачи) для карточек месячного отчёта.

Опциональный третий параметр `questIds` ограничивает расчёт конкретным набором задач — так подключена аналитика проекта/этапа (раздел 9, см. ниже).

Интерфейс: `MonthReport.tsx` — новая карточка «Переносы и точность планирования» (ставка переноса в виде полосы, итоги за всё время, точность оценки, раскрываемый топ-10) и две новые плитки KPI («Переносов за месяц», «Время учтено»). Полный набор графиков по дням/неделям/сферам/приоритетам из раздела 6.2 не реализован в этом этапе — это отдельная визуальная работа, вынесена в «Незавершённое» ниже, чтобы не множить CSS при текущем бюджете стилей (почти 100% лимита, см. `docs/audit/06-ARCHITECTURE_AUDIT.md`).

## 4. Фактическое время (раздел 7)

Ручной быстрый учёт (5/15/30/45/60/90 минут и произвольное значение) уже существовал и оставлен как есть.

Новый таймер — `src/taskTimer.ts`, чистый модуль на `localStorage`: `startTimer`/`pauseTimer`/`resumeTimer`/`finishTimer`/`discardTimer`/`elapsedSeconds`/`formatElapsed`. Переживает перезагрузку страницы, потому что хранится не «тикающий» интервал, а моменты времени (`runningSince`/накопленные секунды) — прошедшее время всегда пересчитывается от сохранённого момента.

**Осознанное ограничение**: таймер привязан к `localStorage` этого устройства/браузера, а не к `GameState`/Firestore. Запущенный на телефоне таймер не будет виден на компьютере — на этом этапе это сознательный компромисс (раздел 19 ТЗ не просил полноценную синхронизируемую модель состояния таймера, а добавление отдельного поля в `GameState` ради одного активного таймера увеличило бы риск конфликтов между устройствами без явной необходимости). Завершение таймера (`finishTimer`) передаёт накопленные минуты в тот же `logTaskTime()`, что и ручной ввод — то есть в общий факт времени и аналитику.

UI — `TaskPlanningFields.tsx`: кнопки «Начать отсчёт времени» / «Пауза» / «Продолжить» / «Завершить» / «Отменить», использующие существующий класс `twin-inline`, без новых стилей.

## 5. Показатели времени (раздел 8)

`timeAnalytics(state, questIds?)` → `plannedMinutes`, `actualMinutes`, `averageDeviationMinutes`, `planAccuracy`, `tasksWithBoth`.

**Formula — Plan Accuracy** (именно точность *оценки длительности*, а не доля выполненных задач): по каждой задаче, у которой заполнены и план, и факт,

```
accuracy(задача) = max(0, 1 − |факт − план| / план)
planAccuracy = среднее accuracy(задача) по всем таким задачам
```

1,0 — оценка точна; отклонение ≥100% от плана даёт 0. `averageDeviationMinutes` — простое среднее `факт − план` (положительное — работа заняла больше времени, чем планировалось).

## 6. Зависимости TickTick, предотвращение ложных переносов (раздел 12, критическое ограничение)

Проверено (read-only, через MCP) на реальной повторяющейся задаче: TickTick Open API v1 отдаёт поле `repeatFlag` (RRULE-строка вида `RRULE:FREQ=DAILY;INTERVAL=30`) **на одном и том же `id` задачи** при каждом новом повторении — то есть API не различает «пользователь перенёс срок» и «наступил следующий повтор той же привычки» одинаковой сменой `dueDate` одного `id`.

Решение: `RemoteTask.repeatFlag` → `remoteFields().tickTickRepeatFlag` → сохраняется как `Quest.tickTickRepeatFlag` (только для чтения, не отправляется обратно в TickTick). `recordTaskSchedule()` помечает `reschedule`-событие как `auto: true`, если на момент изменения у задачи установлен `tickTickRepeatFlag`. `auto`-события:

- **не** входят в `moveCount`/`forwardMoveCount`/`postponementAnalytics`/`monthlyMoves`/`planningMetrics`;
- **остаются** в истории задачи (с пометкой «автоматически (повтор TickTick)»), для прозрачности — пользователь видит полную картину изменений даты, даже если она не считается «переносом».

Честно отражённое ограничение (а не замалчивание): различить вручную перенесённый день повторяющейся задачи от обычного наступления следующего цикла **невозможно** при текущих данных Open API v1 (оба случая выглядят одинаково на уровне API). Поэтому решение сделано в пользу недооценки числа переносов повторяющихся задач, а не переоценки — ложноположительный «перенос» у ежедневной привычки хуже, чем пропущенный реальный перенос.

## 7. Связь с целями/проектами (раздел 9)

`postponementAnalytics()` и `timeAnalytics()` принимают необязательный третий/второй параметр — набор `id` задач. Страница проекта (`GoalWorkspace.tsx`, компонент `Statistics`) собирает задачи текущего проекта (или этапа, если открыт конкретный этап: `q.goalId === goal.id && (!stageId || q.stageId === stageId)`) и показывает карточку «Переносы и фактическое время», отдельную от общей (по всем задачам аккаунта) карточки в месячном отчёте.

Поскольку порог `MIN_SCHEDULED_FOR_RATE = 5` общий, у небольших проектов (меньше 5 задач с плановой датой) ставка переноса, скорее всего, будет показывать «Недостаточно данных» — это ожидаемое и осознанное поведение, а не ошибка.

### 11.2 TickTick: `auto` → `ambiguousRepeat` (критическое исправление счётчика переносов)

Прежняя версия помечала **любое** изменение даты задачи с `tickTickRepeatFlag` как `auto: true` и полностью исключала из счётчика переносов — это неверно: пользователь может и вручную перенести повторяющуюся задачу (пример из ТЗ: ежедневная задача 10 → 12 ноября — это реальный перенос на 2 дня, а не наступление следующего ежедневного повтора).

Решение (`src/planningData.ts`, `repeatStepDays()` + `recordTaskSchedule()`): шаг автоматического повтора разбирается из RRULE (`FREQ`/`INTERVAL`/`BYDAY`). Изменение помечается `ambiguousRepeat: true` **только** если оно (а) вперёд **и** (б) разница в днях совпадает с разобранным шагом повтора, либо шаг нельзя надёжно разобрать (например, `WEEKLY` с несколькими днями в `BYDAY`). Перенос назад или на интервал, не совпадающий с шагом, **всегда** засчитывается как достоверный перенос. Неопределённые случаи не скрываются — они видны в истории задачи и в новом показателе `ambiguousMoveCount()`/`PostponementAnalytics.ambiguousMoves`, с пояснением пользователю, что причина изменения не доказана.

Ограничение (как и раньше, честно): различить вручную перенесённый день повторяющейся задачи от автоматического наступления следующего цикла **невозможно**, когда перенос вперёд совпадает с шагом повтора — у Open API v1 нет для этого отдельного признака. Решение консервативно: такие случаи остаются видимыми как «неопределённые», а не задвоенно засчитываются ни как перенос, ни как «ничего не произошло».

### 11.3 Таймер — надёжность (раздел 3 ТЗ, `src/taskTimer.ts` переписан)

- **3.1 Безопасный порядок**: публичный API разделён на `peekFinish()` (считает секунды и `actionId`, **не удаляет** таймер) и `commitFinish()` (удаляет — вызывается в `TaskPlanningFields.tsx` только после успешной записи времени через `apply()`). `actionId` присваивается один раз при `startTimer()` и сохраняется через все паузы/продолжения той же сессии — повторная попытка «Завершить» после сбоя передаёт тот же `actionId` в `logTaskTime()`, а `addPlanningEvent()` уже умеет отбрасывать повтор события с использованным `id` (защита от задвоения времени). Таймер, сохранённый версией до этого исправления (без `actionId`), получает его лениво при первом `peekFinish()`.
- **3.2 Один активный таймер на пользователя**: `startTimer()`/`resumeTimer()` бросают ошибку, если у того же `ownerId` уже идёт (не на паузе) таймер другой задачи; `TaskPlanningFields.tsx` показывает это предупреждение проактивно (`activeTimer()`), с названием занятой задачи, ещё до попытки нажать «Начать».
- **3.3 Изоляция по владельцу**: ключ `localStorage` теперь `play-your-life-task-timer-v1:<ownerId>` — два аккаунта на одном устройстве/браузере больше не видят и не могут случайно завершить таймер друг друга.
- **3.4 Восстановление**: `isTimerStorageCorrupted()` отличает «данные повреждены» (невалидный JSON/не объект) от «таймеров нет» — интерфейс показывает отдельное предупреждение, а не тихо продолжает как будто таймера не было. Для завершённой задачи с оставшимся неучтённым временем таймера (например, задача была отмечена выполненной в другом месте интерфейса, пока открытое окно всё ещё хранило работающий таймер) добавлен отдельный баннер «Учесть это время / Отменить без учёта» — `logTaskTime()` не проверяет `done`, поэтому время можно зафиксировать и после завершения задачи. Page reload/закрытие и повторное открытие вкладки — уже работали корректно (момент времени, а не «тикающий» интервал, хранится без изменений). Потеря интернета не влияет на сам таймер и на запись факта времени — это чисто локальная операция над `GameState`; собственно синхронизация этого `GameState` с Firestore — общий для всего приложения механизм, не специфичный для таймера, и его отдельная проверка не входила в это исправление.
- **3.5 Округление**: вместо принудительного минимума в 1 минуту (искажавшего короткие сессии) — обычное округление до ближайшей минуты; сессии короче 30 секунд не записываются как факт времени (явное сообщение «Сессия короче 30 секунд — время не учтено», таймер отменяется, время не теряется молча — его изначально и не было, с точки зрения учёта минут). Нижний уровень учёта (целые минуты, 1–43200) не менялся: это существующее ограничение `logTaskTime()`/экономики, не специфичное для таймера, и его изменение расширило бы область правки за пределы ТЗ.

Остаточный риск, зафиксированный честно: между успешным вызовом `apply()` (запись в `GameState` через React `setState`-обёртку) и подтверждением успеха нет синхронного ответа в этой же функции — `apply()` ловит исключение внутри обновляющей функции и uведомляет асинхронно. Для предсказуемых ошибок (задача не найдена, слишком длинная сессия) решение добавляет синхронную проверку перед удалением таймера; непредсказуемый сбой `logTaskTime()` в последний момент остаётся теоретически возможным (хотя полностью безопасным для повтора благодаря устойчивому `actionId`) — полностью транзакционная гарантия потребовала бы менять общий паттерн `apply()`, используемый во всём компоненте и других полях, что выходит за рамки правки, ограниченной таймером.

### 11.4 Аналитика переносов и времени (разделы 4 и 5 ТЗ)

### 11.8 Третий проход (замечания Ивана после зелёного CI, тот же PR #296)

- **Безопасный порядок (3.1), по-настоящему**: `apply()` в `TaskPlanningFields.tsx` теперь возвращает `boolean` по тому же паттерну, что уже используется в `src/components/room3d/RoomEngine.tsx` — пробный синхронный запуск действия против известного состояния решает успех/неудачу для вызывающей стороны (React вызывает функцию-обновитель `onChange(fn)` синхронно, так что это не предположение, а проверка), и только при подтверждённом `true` вызывается `commitFinish()`. Раньше `commitFinish` вызывался безусловно сразу после `apply()`, который сам проглатывал исключение — теперь предсказуемые ошибки (задача не найдена, значение вне диапазона) ловятся синхронно и таймер остаётся сохранённым для повторной попытки.
  - Отдельно проверено (без изменений кода): запись игрового состояния в Firestore — отдельный, уже существующий общий механизм (`src/accountPersistence.ts`), с локальным черновиком (`persistDraft()`), статусами `pending`/`offline`/`conflict` и повторной отправкой при восстановлении связи. Это касается КАЖДОГО поля формы, не только таймера, и единообразно защищает учтённое время таймера после того, как оно подтверждённо попало в `GameState` — отдельный, параллельный механизм ретраев специально для таймера не создавался, чтобы не задваивать уже существующую защиту и не выходить за рамки правки, ограниченной самим таймером.
- **Короткие сессии (3.5), без автоудаления**: сессия короче 30 секунд больше не стирается сама — таймер остаётся на паузе с накопленными секундами; явный отказ от учёта — отдельная, уже существующая кнопка «Отменить» (`discardTimer`). Автоматической потери данных больше нет вообще, только осознанное действие пользователя.
- **RRULE — BYMONTHDAY (3)**: `repeatStepDays()` теперь обрабатывает `BYMONTHDAY` так же, как многодневный `BYDAY` — несколько чисел месяца (например, `BYMONTHDAY=1,15`) делают шаг непредсказуемым, и перенос вперёд остаётся неопределённым, а не ошибочно точным. Добавлены тесты на `MONTHLY` с одним и несколькими `BYMONTHDAY` и на `YEARLY`.
- **Два устройства (5), в пределах доступного**: `actionId` таймера теперь не случайный, а детерминированный — `timer:<taskId>:<момент старта>`. Это не синхронизирует запущенные таймеры между устройствами (сознательно оставленное ограничение, см. выше) и не мешает двум ДЕЙСТВИТЕЛЬНО независимым рабочим интервалам на разных устройствах — оба должны и будут засчитаны отдельно, это не задвоение, а два разных факта. Защита срабатывает именно в узком случае, который реально мог бы привести к незаметному задвоению ОДНОГО интервала: если один и тот же сеанс таймера (тот же `taskId` и тот же момент старта) оказался виден на двух устройствах — например, при синхронизации `localStorage` функцией браузера — оба устройства получат одинаковый `actionId`, и уже существующая защита `addPlanningEvent` по `id` не даст засчитать этот интервал дважды.

### 12.3 Надёжность сохранения таймера

Пересмотрено заново с учётом более жёсткой формулировки ТЗ («подтверждение записи», а не только «синхронная проверка»). Решение не изменилось по сравнению с 11.8: отдельный Firebase-специфичный механизм подтверждения для таймера **не создавался** — по прямому ограничению ТЗ («не перестраивай систему сохранений», «используй существующие механизмы ревизий, идемпотентности и обработки конфликтов»). Вместо этого зафиксирован следующий факт о существующей архитектуре (проверено чтением кода `src/accountPersistence.ts` и `src/AccountRoot.tsx`, без изменений):

- Учтённое время таймера после `apply()` — обычное поле `GameState.events`, а не отдельный канал. Оно проходит ТОТ ЖЕ путь, что и любое другое изменение: `engine.change()` → синхронная эмиссия `{status:'pending', message:'Сохраняем изменения…'}` → синхронная запись локального черновика (`persistDraft()`) → отложенная отправка в Firestore (`flush()`).
- Статус-бар аккаунта (`AccountRoot.tsx`, строки ~332–357, передаётся во `App` как `accountTools` и виден постоянно, не только на экране загрузки) уже показывает этот статус пользователю: `role="status"` со значением `unit.snapshot.message` («Сохраняем изменения…» во время записи, текст ошибки при `offline`/`error`, и отдельное `role="alert"`, если сам браузер не может сохранить локальный черновик). Это ОБЩИЙ, не специфичный для таймера индикатор — он устраивает требование раздела 3.2 («пользователь видит статус «Ожидает сохранения»») в точности в том смысле, что пользователь видит, что сохранение ещё не завершено, и видит ошибку, если она произошла, — без создания второго, таймерного механизма.
- `commitFinish()` (удаление локальной сессии таймера) вызывается, только когда `apply()` вернул `true` — то есть когда действие по счётчику учтённого времени УЖЕ синхронно прошло внутри `engine.change()` (включая синхронную запись локального черновика). Если дальнейшая отправка в Firestore завершится ошибкой, запись о факте НЕ теряется: она уже часть `GameState`, сохранённого локально, и будет отправлена повторно при следующем успешном `flush()` — как любое другое поле состояния.
- Остаточный, осознанно принятый предел (как и в 11.9): если именно синхронная запись локального черновика провалится РОВНО в момент между `apply()` и `commitFinish()` (например, квота `localStorage` закончилась), это будет видно через существующий alert «Браузер не сохраняет изменения…», но не отдельно для этой конкретной записи времени, а как общее состояние аккаунта. Отдельный, специально протоколируемый для таймера статус «Ожидает сохранения» с явным retry-UI не реализован — это требовало бы передавать статус сохранения аккаунта как проп через `TaskWindow` → `TaskPlanningFields`, что выходит за рамки точечной правки одного модуля.

### 12.3.4 Секундная точность (раздел 3.4)

Не внедрялась. `logTaskTime()` и вся связанная аналитика (`actualMinutes`, `timeAnalytics`, `monthlyActualMinutes`) используют целые минуты как контракт данных; переход на секунды потребовал бы либо дублирующего поля, либо миграции формата событий — оценено как риск, не оправданный разделом 3.4, который сам отмечен как «по возможности» (не обязательное требование). Уже внедрённое поведение коротких сессий (не удаляются автоматически, доступны для повторной попытки) сохранено без изменений.

### 12.4.2 «Пропущенные повторения» TickTick

Явного отдельного кода для многошаговых («пропущенных») автоматических переносов нет, и осознанно не добавлялся. Логика `repeatStepDays()`/`recordTaskSchedule()` в `src/planningData.ts` устроена так, что:

- Единственная категория, которая может скрыть достоверный перенос, — `ambiguousRepeat` («Неоднозначно»), и событие в неё попадает ТОЛЬКО когда сдвиг вперёд совпадает с ожидаемым шагом повтора (или шаг не удаётся разобрать). Многошаговый автоматический скачок (например, на 3 шага у ежедневной задачи, если TickTick когда-либо так делает) НЕ совпадёт с шагом в один день — такое событие будет засчитано как достоверный перенос пользователя, а не скрыто и не помечено «подтверждённо автоматическим» (такой категории вообще не существует — см. 12.7).
- Это умышленно консервативное, безопасное в сторону требования ТЗ решение: «если происхождение изменения достоверно не определяется — оставлять в категории «Неоднозначно»; не считать подтверждённо автоматическими» — у нас вообще нет пути, которым событие могло бы быть скрыто или ошибочно отнесено к автоматическим без доказательства.
- Изменений кода не требовалось; решение документируется здесь явно, так как в предыдущем проходе оно было принято, но не зафиксировано письменно.

### 12.4.3 Сохранение данных переносов

Проверено чтением кода (без новых тестов в этом проходе, кроме уже перечисленных в 11.7):
- Перенос фиксируется один раз: `addPlanningEvent()` проверяет `state.events.some(e => e.id === id)` и не создаёт дубликат.
- Повторная синхронизация не увеличивает счётчик: `recordTaskSchedule()` создаёт событие только когда `from !== to` (дата реально изменилась); неизменная дата при повторном `/api/project/.../data` не создаёт события.
- История сохраняется после выполнения: события в `state.events` не зависят от `task.done`, не удаляются при завершении задачи.
- Старые задачи открываются без ошибок: новые поля (`ambiguousRepeat`, `direction`) опциональны, старые события без них валидны (`validPlanningEvent` не требует их).
- Удаление задачи в TickTick не стирает историю незаметно: `state.events` хранит `sourceId`, независимая коллекция; при удалении задачи в игре (`removeQuest`) история НЕ удаляется автоматически — остаётся в архиве событий (как и остальная история игры). Отдельного теста на этот конкретный путь («удалили в TickTick → у нас задача тоже исчезла по правилу `deleteRemote`/ручному удалению → история цела») не добавлено в этом проходе — известное ограничение покрытия.
- Связи с проектами/целями: событие сохраняет `goalId`/`stageId` в момент создания (см. `addPlanningEvent()`), не пересчитывается при последующих изменениях задачи — соответствует ожиданию.

### 12.6 Статус синхронизации TickTick

**Новое в этом проходе.** Использован исключительно существующий механизм состояния интеграции (`useTickTick.ts`/`TickTickContext`) — отдельный сервис синхронизации не создавался.
- Добавлен флаг `lastSyncError: boolean` (`useTickTick.ts`, `tickTickContext.ts`) — отдельно от текста `status`, чтобы не выводить состояние ошибки разбором сообщения. Устанавливается `true` при исключении в `sync()` и при раннем выходе «Нет сети», `false` при успешном (в т.ч. частично прерванном, но не выбросившем исключение) обмене.
- `TickTickConnection.tsx`: строка «Последняя попытка обмена» заменена на явное «Последняя успешная синхронизация: …» или «Последняя попытка обмена завершилась ошибкой: … Задачи могут быть не актуальны — повторите синхронизацию или переподключите TickTick» — пользователь теперь видит факт ошибки явно, а не выводит его из текста.
- Добавлено отдельное предупреждение «Подключение потеряно — нужно переподключение», когда доступ утрачен (`!ready`) после того, как подключение уже когда-то работало (`c.lastSync` существует) — с указанием времени последней успешной синхронизации.
- Существующие индикаторы `dirty` («Есть несохранённые настройки») и бейдж «Подключён»/«Не подключён» не менялись — они уже покрывали «есть ли ожидающие изменения» и «подключено ли».
- Регрессионный тест — `tests/ticktick-ui.mjs`: в уже существующем сценарии потери сети (`ctx.setOffline(true)`) добавлена проверка текста об ошибке, затем после восстановления — проверка возврата к «Последняя успешная синхронизация» и отсутствия следа ошибки.

### 12.7 Аналитика — повторная проверка

Код `src/planningData.ts` прочитан заново против всех 7 пунктов ТЗ; изменений не требовалось, все уже выполнены в предыдущих проходах:
1. Будущие события не включаются в статистику периода — верхняя граница `weekTo`/`monthTo` в `postponementAnalytics()`.
2. Текущий месяц не смешивается со всей историей — `monthlyMoves()`/`monthlyActualMinutes()` отдельно от `totalMoves`/`actualMinutes`.
3. Незавершённые задачи не считаются итогом точности — `planAccuracy`/`averageDeviationMinutes` требуют `task.done`.
4. Неизвестное фактическое время не подменяется нулём — проверка `actual` (falsy) исключает задачу из расчёта, а не подставляет 0.
5. Задачи с готовой датой при импорте учтены — `scheduledTaskIds` включает текущие `dueAt`/`startsAt`, не только события истории.
6. Двойной учёт событий исключён — `addPlanningEvent()` дедуплицирует по `id`.
7. Разделение подтверждённых/неоднозначных переносов сохранено — `ambiguousMoveCount`/`ambiguousMoves` отдельно от `moveCount`/`totalMoves`.
